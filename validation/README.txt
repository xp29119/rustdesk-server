RustDesk Stage 2 — real hbbs/hbbr black-box protocol validation

Scope
-----
This harness starts the reviewed, compiled server executables supplied on the CLI.
It never imports a server implementation or substitutes a Python server model.
The test client is Python + PyNaCl/libsodium; reports explicitly state:
  real_server_process: true
  actualClient: false
It does NOT run the shipped RustDesk Mac/Windows/Android/iOS binary, capture a
screen, validate OPPO unattended access, or verify App Store behavior.

The default nonempty account token is random synthetic opaque text. This exercises
the official client's key+token secure protocol path. This hbbs build does not
validate account tokens, so a successful exchange is NOT evidence of API login,
server account authorization, or relay-abuse prevention. API tests are separate.
An optional private --account-token-file can supply an issued token, but this
harness still does not verify its issuance or its account permissions.

Dependencies and execution
--------------------------
Linux, Python 3.10+, util-linux (unshare), iproute2 (ip), and requirements.txt.
Run on the dedicated ephemeral GitHub ubuntu-22.04 build runner. No Docker,
Flutter, Android SDK, browser, or production server access is needed.

Example from the server repository root after cargo build --release --bins:

  python3 -m venv .validation-venv
  .validation-venv/bin/python -m pip install -r validation/requirements.txt
  sudo "$PWD/.validation-venv/bin/python" validation/protocol_blackbox.py \
    --hbbs "$PWD/target/release/hbbs" \
    --hbbr "$PWD/target/release/hbbr" \
    --report "$PWD/validation-results/protocol-blackbox-result.json" \
    --keep-logs

The dependency installation happens BEFORE isolation. The harness itself downloads
nothing. sudo is used solely so unshare --net and ip link/addr work consistently on
GitHub. It modifies no host interface, host firewall, or external server. Without
root it tries an unprivileged user+network namespace; if the runner disables that,
it fails closed and never starts wildcard listeners on the host network.

The script creates its own NEW network namespace, verifies a changed namespace ID
and that only lo exists, then enables lo and adds 10.203.0.1/32 and 10.203.0.2/32
there. The native servers bind their original wildcard listeners inside that
namespace. All clients bind 10.203.0.2 and connect only 10.203.0.1. There is no veth,
DNS configuration, external interface, or outbound route. The two non-127 IPs on
lo are necessary: official hbbr and the hbbs NAT/online port interpret a 127/8
source as a text management command, not the native client protocol.

Base port is 32116, overridable using --port (must be unprivileged). Ports inside
the namespace: hbbs UDP/TCP p, NAT/online p-1, hbbs WS p+2, hbbr TCP p+1, WS p+3.
WebSockets are not exercised by this suite. Generated private keys, SQLite data,
synthetic account token, and temporary HOME are removed after stopping the owned
process groups. No user config is loaded. Optional logs are redacted for the token
and retained with 0600 mode in protocol-blackbox-logs; no private key is copied.

Exit code 0 means all 14 real-process cases passed; 1 means a startup/test failure;
2 means bad invocation, dependencies or isolation unavailable. The JSON contains
per-case outcomes, binary SHA-256, public-key fingerprint, and limits of the claim.
Do not publish a green status unless the JSON has all expected cases and passed=true.

Local tooling-only verification (safe on Mac):
  ../stage1/compatibility/.venv/bin/python validation/protocol_blackbox.py --self-check
Adjust the venv path relative to the current directory. This mode runs no server,
creates no listener, and explicitly prints real_server_process=false. It is not an
integration substitute.

Cases and meaningful acceptance criteria
---------------------------------------
1. Unlogged native UDP RegisterPeer -> request_pk, RegisterPk -> OK, subsequent
   RegisterPeer -> no key request. Plaintext online query on p-1 returns an online
   bit for the registered peer and offline for an unknown peer.
2. Verify the actual server's Ed25519-signed ephemeral X25519 key using the public
   file generated by hbbs. Complete legacy version-0 exchange, then encrypted
   PunchHoleRequest including synthetic account token. A registered target gets
   the native notification and sends the native TCP LocalAddr/PunchHoleSent reply.
   The controller decrypts the deferred response and verifies the signed target
   ID/public key. This covers the writer state transferred to the pending sink.
3. Unlogged TCP punch sends plaintext BEFORE reading. The harness follows the
   official two-frame receive budget, observes exactly one skipped KeyExchange,
   then receives plaintext ID_NOT_EXIST. It does not arbitrarily discard frames.
4. Wrong configured signing public key fails CLIENT signature verification;
   application bytes sent after that failure are zero. This direction matters:
   the server never receives the client's configured trust public key.
5. Correct crypto with wrong licence_key receives encrypted LICENSE_MISMATCH.
6. Seven malformed handshake field-length/count variants close the connection.
7. Correct-sized but corrupted encrypted symmetric key closes the connection.
8. Truncated protobuf first frame closes the connection.
9. A 1 MiB + 1 declared main-TCP frame, no body, closes before and after exchange.
   This tests the reviewed 1 MiB frame cap. The test never sends an enormous OOM
   allocation request, and does not assume a new cap on hbbr/NAT/WebSocket.
10. Corrupted SecretBox payload plus an immediately appended valid plaintext
    request closes the connection without plaintext recovery.
11. Two interleaved connections have different ephemeral keys and independent
    send/receive counters. Cross-connection ciphertext closes the wrong connection
    while the correct connection can still decrypt the matching response.
12. Unsupported UDP PunchHoleRequest with valid server key targeting both a
    missing and a registered peer produces no reply to caller or target. A normal
    registration heartbeat then still succeeds, proving UDP wasn't simply dead.
13. Two actual hbbr clients pair by UUID/key; three independently encrypted opaque
    payloads in each direction pass byte-for-byte and decrypt at the receiver.
14. hbbr rejects a wrong licence key, then a fresh valid relay pair still works.

Every malformed hbbs case is followed by a fresh successful encrypted NAT request
and liveness check of both processes. Connection-local failures must not be counted
as a pass if the server died. One-byte or empty crypto frames are not used as the
bad-ciphertext oracle because the legacy library has special heartbeat handling.

Protocol connections generally return one application response then close or move
their sink. We do not invent a repeated-request keepalive protocol to test counters;
the independent counter property is checked with interleaved actual connections,
and deeper multi-message state transitions remain covered by Rust unit tests.
